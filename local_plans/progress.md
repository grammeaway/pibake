- **Pi is 1.3.0, not 1.2.0.** Re-checked what l1 depends on. `parseSource`, `parseNpmSpec`, `getPackageIdentity`, `getNpmInstallPath`/`getGitInstallPath`, `collectPackageResources`, `resolveExtensionEntries`, `collectAutoExtensionEntries` and `readPiManifest` are in the unminified `dist/core/package-manager.js`, `dist/core/pi-manifest.js`, `dist/utils/git.js` and `dist/utils/paths.js`; the port cites them. The doc line numbers cited in `README.md` (e.g. `packages.md:100-119`, `cli.md:196`) should be re-checked by the plan that uses them.
- **Inventory shape, beyond the plan's list:** each package carries its raw entry (`source`, `filter`, string vs object form kept, because Pi resolves `{"source": x}` differently from `"x"`), `parsed` source, `identity`, `install_path`, and `installed` (`null` when absent) with `version` (for l3), `manifest` (`pi` or `conventional`), resolved `extensions` entry points, declared `skills`/`prompts`/`themes` roots, and `unresolved`. Top level adds `settings_resources` (the raw resource arrays) and `install_roots`.
- **Resolution depth:** extension entry points are resolved by Pi's rules (manifest files and directories, `index.ts`/`index.js`, conventional `extensions/`, and which of manifest or conventional applies per entry form). Manifest globs, `!`/`+`/`-` patterns and missing paths are listed under `unresolved` with a reason, never dropped. Settings filters are reported, not applied. Skills, prompts and themes are listed as declared roots only (D6 reads them at runtime).
- **Added:** a `PIBAKE_E2E=1` oracle test runs Pi's own `DefaultPackageManager.resolve()` (from the installed Pi, on a scratch copy of the fixture) and asserts it finds the same extension entry points. Run by hand on a copy of the live setup minus credentials and state: the same 16 entries (12 packages, 4 local files) from both.
- **Hand check on the live setup (step 5):** 12 packages (11 npm, 1 git), each installed with its extension entry, nothing unresolved; the 4 local extension files; `auth.json` under state by name. ## Found

Bugs or debts found during a pass and kept out of its diff.

- **l1 → l5: let Pi resolve what to bake.** Pi's resource resolution is bigger than the inventory needs: minimatch globs, `!`/`+`/`-` patterns, `.gitignore`/`.ignore`/`.fdignore` files, the string-vs-object fallbacks, `hosted-git-info` shorthands, a legacy global npm root. Porting all of it to Rust invites drift on every Pi release. Suggestion for l5's entry generator: get the enabled extension list from the staged Pi's `DefaultPackageManager.resolve()` (as `extension_entries_match_pis_resolver` already does), and keep the Rust inventory for reporting and locking. Owner or l5 call. *Settled in l5: Pi's own pipeline decides (see Decisions).*
- **l1 → l5: built-in extensions.** Pi 1.3.0 has four built-ins, toggled per user with `-builtin:<name>` in `settings.json` `extensions`. Whatever double-loading guard l5 picks must keep the user's toggles. *Settled in l5: Pi's own pipeline decides (see Decisions).*
- **l1 → l5: load order.** Pi discovers directory contents in `readdir` order; the inventory sorts. If extension order affects behaviour (command or tool name conflicts), l5 must take Pi's order, not the inventory's. *Settled in l5: Pi's own pipeline decides (see Decisions).*
- **l1 → l2: skills outside the agent dir.** Pi also loads skills from `~/.agents/skills` (and project `.agents/skills` up to the git root). `verify` runs must control `HOME` to compare like with like.
- **l1 → l7: state keys inside `settings.json`.** `lastChangelogVersion` (and others Pi writes) change without the setup changing. Staleness hashing must ignore them; the inventory does not split keys yet.
- **Shortcuts in code** (`shortcut:` comments): `file://` URLs not percent-decoded; git URLs split textually without WHATWG normalisation, `%` rejected; legacy global npm root not consulted; ignore files and `readdir` order not ported.
- **l2 → l11: the big write is slow.** 200 KB in 20-byte deltas takes about 54 s of CPU on stock Pi, almost all of it without extensions too (`-ne`: 52 s). That fits verdict #7, but l11 should profile whether `parseStreamingJson` is all of it or whether per-delta event work (`toolcall_delta` carries `partial: output`) adds to it. It also makes a 20-run bench take about 20 minutes per command.
- **l2 → l5: extensions cost ~2.6 s of startup** (indicative: 3.2 s with them, 0.55 s with `-ne`).
- **l2 → l5: command paths.** `get_commands` reports `sourceInfo.path` and `baseDir` of each extension command (e.g. `<agent_dir>/extensions/init.ts`). A bundle will report something else. l5 decides whether the bundle keeps these paths or `verify` compares baked extension commands without them. *Settled in l5: Pi's own pipeline decides (see Decisions).*
- **l2: side traffic seen under the harness.** `pi-observational-memory` makes its own model calls after each turn, on the current model. `pi-observational-memory` and `@grammeaway/pi-cook` emit `extension_error` "ctx is stale" on `agent_settled` in `--mode rpc --no-session` runs (upstream, harmless to `verify`). Pi creates `auth.json` and `models-store.json` in an agent dir that lacks them.
- **l2 step 6: interactive time-to-prompt** through a pseudo-terminal is not built. RPC readiness is the startup metric; add a pty metric if l6 or l10 needs time-to-first-paint.
- **l3 → l4: npm flags.** The npm lock was resolved with `--legacy-peer-deps`; `npm ci` in the stage must pass it too, or npm solves peers the lock never had.
- **l3 → l4: no `package.json` is stored.** `pibake.package-lock.json`'s root entry (`packages[""]`: `name`, `dependencies`) is the generated `package.json`; l4 rebuilds it from there (adding esbuild re-pins, as l4 plans).
- **l3 → l4: git package dependencies are not locked.** Pi runs `npm install --omit=dev --legacy-peer-deps` inside git packages; their trees are outside the npm lock. Ponytail has no dependencies, so nothing is lost today.
- **l3 → l7: reuse `lock::Setup`.** It reads exactly what the staleness fingerprint needs for packages (npm versions, git HEADs, Pi version).
- **l3: where the live lock lives.** Without a `pibake.toml`, `pibake lock` writes into the working directory, which in this repo is the repo itself. Owner call: a local-mode `pibake.toml` somewhere outside the repo, or ignore `pibake.lock`/`pibake.package-lock.json` here.
- **l4 → l6: `build` should run the lock's drift check before staging.** `stage` installs the lock as written; if the setup has moved on, the build would silently differ from stock Pi.
- **l4 → l5: stage layout** for the entry generator: `node_modules/` (Pi, npm packages, esbuild), `git/<host>/<path>/` (checkout with `.git`), `local/extensions/` (a copy of the agent dir's `extensions/`). Pi is at `node_modules/@earendil-works/pi-coding-agent`.
- **l4: the stage key covers the pibake version, not pibake's stage code.** While pibake stays at 0.1.0, a change to what `stage` writes (e.g. in l5) reuses older stages; bump the version or delete `target/pibake/stage/` when that happens.
- **l4: disk.** Each stage is ~266 MiB and none are removed; a stage killed by a signal also leaves its `.tmp-*` directory. `pibake clean` is the plan's non-goal; revisit when disk use bites. Any change to `extensions/` re-runs `npm ci` and the git clone (~6 s warm), since the hash is one key for the whole stage.
- **l5: behaviour differences of the bundle** (none visible to `verify`): baked modules persist across `/reload` (jiti's `moduleCache: false` re-evaluates); dependencies shared by several extensions are one instance, not one per extension; edited extension source is not picked up until rebuilt (l7: staleness); the hoisted stage `node_modules` could let an extension resolve a dependency it does not declare; `pi update`/self-update acts on the global install, not the bundle.
- **l5: eager OAuth and AWS SDK.** Registering OAuth flows and Bedrock statically evaluates 9 OAuth modules and the AWS SDK at startup. Candidate for l8/l9.
- **l5 → l6: SEA layout.** The bundle relies on its `node_modules` link (Pi package dir, optional deps, workers beside `dist/bundle/chunks`). l6 must decide what of the stage ships next to the executable.
- **l5: disk.** Each bundle is ~66 MB (mostly the source map), none removed.
- **l5: stage reuse.** l5 did not change what `stage` writes, so l4's stages stay valid.
- **l3: `npmCommand`.** A `settings.json` `npmCommand` of pnpm or bun leaves no npm lock to seed from; pibake still locks with npm. Not used on this setup.
- **l6 → l7: the executable embeds the host's `node`.** Arch's `/usr/bin/node` is dynamically linked (`libicu`, `libssl`, `libuv`, `absl`, …), and so is the SEA: a system library upgrade can break it until rebuilt, and the lock's `[node] version` does not see a same-version repackage. l7's staleness check could include the `node` binary's hash; a static official Node build would avoid it (owner call: source of the embedded Node).
- **l6: SEA divergences** (none visible to `verify`): non-literal `import()` of files throws in the executable where `node pi.mjs` would import: pi-btw's `btw-ssh-workspace.ts` importing `pi-ssh-remote` source (not installed here, so it fails either way) and pi-web-access's macOS `glimpse` (fails to `null` on Linux). Optional native deps (`bufferutil`, `utf-8-validate`) resolve from the extracted root, where they are not, so `ws` uses its JS paths (as in the stage, where they are not installed either). Self-update detection sees the executable, not an npm install.
- **l6: bench and the cache.** The harness gives each run a fresh `HOME`, so every executable run extracts its 14 MiB again. The cost is within noise today; if it is not under the recorded bench, pass `XDG_CACHE_HOME` through for executables.
- **l6: disk.** `~/.cache/pibake/<hash>/` (14 MiB) per distinct asset set, never removed (the plan's non-goal). `target/pibake/bin/` holds one executable per name.
- **l6: no static `--version` without the prologue.** `pi-baked --version --foo` prints `1.3.0` (Pi's), not the pibake line.
- **l6: `build` always reruns `--build-sea`** (3–15 s, load-dependent) even when nothing changed. Skipping it needs a key over the bundle hash, the asset hash, pibake's version and the `node` binary; add it if the wait bites (l7 has the same inputs).
- **l6 → l7: where the build-time fingerprint goes.** Into the executable's `pibake.json` SEA asset (beside `version`, `hash`), not into the bundle: the bundle is content-keyed, and extension mtimes in it would rebuild it without a code change. The prologue already reads `pibake.json` before Pi starts, in the SEA branch only. Keeping the recorded components (packages entries, npm versions, git HEADs, `extensions/` sizes/mtimes/sha256, Pi version) instead of one hash lets the runtime name what changed.
